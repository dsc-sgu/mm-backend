# Concurrency control for course editing

- Status: proposed
- Deciders: Ezhkin-Kot
- Date: 2026-03-15

Technical Story: Реализация механизма редактирования курсов с защитой от конфликтов из-за одновременного редактирования.

## Context and Problem Statement

Необходимо правильно обрабатывать ситуацию, когда два преподавателя одновременно пытаются редактировать один курс, так как иначе это приведёт к потере данных и race condition.
Ранее было принято решение просто блокировать возможность редактирования курса, если в этот момент он уже редактируется кем-то другим. Иной подход потребовал бы слишком сложной логики работы, что на данный момент не кажется целесообразным.
Как обеспечить удобный UX (предупреждение о блокировке) и гарантированную целостность данных в БД, обрабатывать возможные проблемные ситуации, а также подготовить почву для дальнейшего улучшения механики редактирования курсов?

## Decision Drivers

- Data Consistency: Ни при каких условиях изменения одного пользователя не должны молча затираться другим.
- User Experience: Пользователь должен знать, что курс уже кем-то редактируется, до того как потратит время на свои правки.
- Fault Tolerance: Система должна корректно обрабатывать обрывы связи и закрытие вкладок (проверять, точно ли курс ещё редактируется).
- Future Proof: Возможность добавить автоматическое кэширование промежуточных изменений при редактировании курса.

## Considered Options

### Optimistic Concurrency Control

Механизм, основанный на версии записи в основной базе данных без какого-либо предварительного резервирования доступа.

- При загрузке курса клиент получает текущий номер версии (например, `version: 1`). При сохранении изменений клиент отправляет эту версию обратно. Бэкенд выполняет запрос: `UPDATE courses SET ..., version = 2 WHERE id = <id> AND version = 1`.
- Если с момента загрузки версию успел обновить кто-то другой, запрос обновит 0 строк, и система вернет ошибку.

#### Pros and Cons of the Option

- Good: Очень простая реализация, не требует кэша.
- Bad: Плохой UX: пользователь узнает о конфликте только в момент сохранения, теряя всю проделанную работу.

### Database-Level Pessimistic Locking

Жёсткая блокировка записи непосредственно в БД на всё время сессии редактирования.

- При нажатии кнопки редактирования в таблице `courses` устанавливается флаг `is_locked = true` и `locked_by = user_id`. Либо открывается транзакция с `SELECT FOR UPDATE`, которая держится открытой до конца редактирования.
- Никто другой не сможет начать правки, пока первый пользователь явно не завершит редактирование.

#### Pros and Cons of the Option

- Good: Гарантированная блокировка на уровне БД.
- Bad: Риск "мертвых" блокировок: если сервер упал или клиент ушел, курс останется заблокированным до ручного вмешательства.
- Bad: Высокая нагрузка на БД при частых проверках.

### Distributed Lock with Heartbeat

Мягкая блокировка в Dragonfly/Redis, работающая по принципу аренды (lease).

- Блокировка создается в кэше с коротким временем жизни (TTL, например, 60 секунд). Пока пользователь держит вкладку открытой, фронтенд автоматически отправляет сигнал (Heartbeat) каждые 30 секунд, продлевая аренду.
- Если пользователь свернёт вкладку или у него надолго пропадёт связь, блокировка сама исчезнет через минуту, освободив курс для редактирования.

#### Pros and Cons of the Option

- Good: предотвращает конфликты до начала работы, сразу переводя интерфейс других пользователей в Read-only.
- Good: механизм TTL (Time To Live) в Dragonfly автоматически освобождает курс, если пользователь перестал проявлять активность или у него пропал интернет.
- Good: позволяет отображать в UI, кто именно сейчас работает над курсом.
- Bad: существует риск race condition: если блокировка в кэше истечет из-за лага сети одновременно с тем, как пользователь A нажмет на сохранение, а пользователь B в этот же момент перехватит блокировку, данные A могут затереть данные B, и B будет работать с неактуальным состоянием курса.
- Bad: требует максимально стабильной работы Dragonfly, так как от него зависит вся система.

### Hybrid Locking

Комбинация Optimistic Concurrency Control (для физической целостности данных) и Distributed Lock with Heartbeat (для управления доступом в интерфейсе).

- Мы используем Dragonfly для управления правом на редактирование в реальном времени, но финальное сохранение в Postgres всё равно сопровождается проверкой `version`.
- Это исключает редкие race conditions (например, если блокировка в кэше истекла прямо в момент сохранения) и обеспечивает максимальную надежность при возможности реализовать удобный UX.

#### Pros and Cons of the Option

- Good: Сочетает лучший UX и максимальную надежность.
- Good: Оптимистичная блокировка (`version` в Postgres) служит страховкой на случай сбоя кэша или редких сетевых задержек, когда TTL блокировки истёк преждевременно.
- Good: Удобно для последующей реализации промежуточного кэширования (Drafts).
- Bad: Сложность реализации: требует синхронной работы фронтенда, Dragonfly и Postgres.

## Decision Outcome

Chosen option: "Hybrid Locking", так как это решение разделяет ответственность: Dragonfly обеспечивает механизм Heartbeat и возможность отображать блокировку на фронтенде, а Postgres гарантирует финальную целостность транзакции.

## Positive Consequences

- Конфликты предотвращаются на раннем этапе (при блокировке возвращаем `423 Locked`).
- Данные защищены версионированием даже при сбое кэша или сети.
- Появляется готовое место для будущего хранения промежуточных черновиков (Drafts) в Dragonfly.
- Снижение нагрузки на основную БД (проверки Heartbeat не затрагивают Postgres).

## Negative Consequences

- Фронтенд должен поддерживать фоновые запросы (Heartbeat) во время редактирования.

## Implementation Details

- В таблице `courses` добавляется поле `version INTEGER NOT NULL DEFAULT 1`. Возможно будет полезно добавить индекс для поиска по ID курса и его версии: `CREATE INDEX idx_courses_id_version ON courses(id, version);`
- Блокировка в Dragonfly реализуется путём добавления ключа `lock:course:{uuid}` в формате `string` с установленным TTL. Значением является `user_id` пользователя, начавшего редактирование. TTL = 60 секунд.
- Каждые 30 секунд фронтенд должен отправлять Heartbeat в виде запроса `POST /lock`. При получении этого запроса на бэкенде происходит проверка, что автор является владельцем блокировки и обновление TTL в Dragonfly.
- При запросе на сохранение сделанных пользователем изменений открываем транзакцию, в которой:
  - проверяем в ней версию курса и блокируем его в БД на время транзакции;
  - удаляем все старые блоки курса из БД;
  - в цикле добавляем в БД все новые отредактированные блоки;
  - инкрементируем версию курса;
  - удаляем блокировку из Dragonfly;
  - коммитим транзакцию в Postgres.
- Если Heartbeat не пришёл вовремя, блокировка в Dragonfly снимается автоматически. Если в это время кто-то другой перехватил блокировку, то при попытке Heartbeat запроса предыдущий пользователь получит `409 Conflict`, фронтенд должен правильно такую ситуацию обрабатывать.
- Вариант с полной заменой всех блоков курса в БД при сохранении выбран потому, что это гарантирует их правильный порядок при перестановке пользователем и упрощает код, однако у такого подхода есть минус, что могут сбиваться ID у блоков и какие-то связи в БД с этими блоками по их ID могут поломаться. Ещё есть вариант реализовать это через `UPSERT`, то есть проверку существования такого блока в БД, и либо его обновление, либо создание нового, если такого блока нет.
