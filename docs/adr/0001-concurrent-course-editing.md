# Механика редактирования курсов

## Проблематика

Необходимо реализовать механизм редактирования курса преподавателем. При этом нужно правильно обрабатывать ситуацию, когда два преподавателя одновременно пытаются редактировать один курс, так как иначе это приведёт к потере данных и race condition. Также стоит добавить возможность версионирования и отката сделанных изменений.

Как обеспечить удобный UX редактирования курсов, возможность отмены изменений и гарантированную целостность данных в БД, обрабатывать возможные проблемные ситуации, а также оставить удобную возможность для дальнейшего улучшения?

## Факторы, влияющие на решение

- Ни при каких условиях изменения одного пользователя не должны молча затираться другим.
- Пользователь должен знать, что курс уже кем-то редактируется, до того как потратит время на свои правки.
- Возможность пользователя потерять несохранённые изменения должна сводиться к минимуму.
- Не должно быть длительных блокировок в БД.
- Не должно быть огромных по объёму запросов.
- Студенты не должны видеть промежуточное состояние курса в процессе редактирования.
- Нужно где-то хранить предыдущие версии редакций курса, чтобы пользователь мог откатить свои изменения.
- Система должна не допускать зависших блокировок (проверять, точно ли курс ещё редактируется), но при этом корректно обрабатывать обрывы связи.

---

## Рассматриваемые решения

### 1. Оптимистичная блокировка, один запрос на обновление всего курса

Механизм, основанный на версии записи в основной базе данных без какого-либо предварительного резервирования доступа. При завершении редактирования фронтенд шлёт один запрос на обновление курса со всем его содержимым.

- При загрузке курса клиент получает текущий номер версии (например, `version: 1`). При сохранении изменений клиент отправляет эту версию обратно. Бэкенд выполняет запрос: `UPDATE courses SET ..., version = 2 WHERE id = <id> AND version = 1`.
- Если с момента загрузки версию успел обновить кто-то другой, запрос обновит 0 строк, и система вернет ошибку.

#### Плюсы решения

- Максимально простая реализация.

#### Минусы решения

- Плохой UX: пользователь узнает о конфликте только в момент сохранения, теряя всю проделанную работу.
- Большой и тяжёлый запрос, потребность в конструировании такого же большого `UPSERT` запроса SQL.
- Отсутствие возможности отката изменений.

---

### 2. Мягкая блокировка с TTL, отдельные запросы

Мягкая блокировка в Redis, работающая по принципу аренды (lease). Изменения каждого блока приходят в виде отдельных небольших запросов.

- Блокировка создается в кэше с коротким временем жизни (TTL, например, 60 секунд). Пока пользователь держит вкладку открытой, фронтенд автоматически отправляет сигнал (heartbeat) каждые 30 секунд, продлевая аренду.
- Если пользователь свернёт вкладку или у него надолго пропадёт связь, блокировка сама исчезнет через минуту, освободив курс для редактирования.
- При каждом изменении отдельных частей курса фронтенд шлёт запрос только с этими изменениями.

#### Плюсы решения

- Предотвращает конфликты до начала работы, сразу переводя интерфейс других пользователей в Read-only.
- Механизм TTL (Time To Live) в Redis автоматически освобождает курс, если пользователь перестал проявлять активность или у него пропал интернет.
- Позволяет отображать в UI, кто именно сейчас работает над курсом.
- Сделанные изменения сразу сохраняются и не будут утеряны.

#### Минусы решения

- Существует риск race condition: если блокировка в кэше истечет из-за лага сети одновременно с тем, как пользователь A нажмет на сохранение, а пользователь B в этот же момент перехватит блокировку, данные A могут затереть данные B, и B будет работать с неактуальным состоянием курса.
- Отсутствие возможности отката изменений.
- Промежуточное состояние курса в момент редактирования сразу отображается у студентов.

---

### 3. Мягкая + оптимистичная блокировка, отдельные запросы, снапшоты курсов

Комбинация оптимистичной блокировки на уровне Postgres (для физической целостности данных) и мягкой блокировки на уровне Redis (для управления доступом в интерфейсе). Отдельные запросы при изменении каждого блока. Версионирование курсов по снапшотам: каждая новая редакция курса (новая версия) является отдельным снапшотом.

- Запись о блокировке в Redis с TTL для управления правом на редактирование в реальном времени, но финальное сохранение в Postgres всё равно сопровождается проверкой `version`.
- При каждом изменении отдельных частей курса фронтенд шлёт запрос только с этими изменениями.
- Добавляется механика снапшотов:
  - объект таблицы `courses` хранит поле, указывающее на актуальный снапшот курса;
  - снапшот - курс с его содержимым на определённым момент времени;
  - при начале редактирования курса создаётся новый снапшот, над ним проводятся все изменения, затем, при завершении редактирования, этот снапшот курса становится в upstream, то есть то поле объекта в `courses` начинает указывать на него;
  - пользователь может откатить свои изменения на предыдущие снапшоты

#### Плюсы решения

- Сочетает лучший UX и максимальную надежность.
- Оптимистичная блокировка (`version` в Postgres) служит страховкой на случай сбоя кэша или редких сетевых задержек, когда TTL блокировки истёк преждевременно.
- Сделанные изменения сразу сохраняются и не будут утеряны.
- При этом студенты не видят редактируемую версию курса, так как это происходит в отдельном снапшоте.
- Появляется возможность отката изменений на этап до начала редактирования.

#### Минусы решения

- Объём изменений между снапшотами может быть достаточно большим (нельзя откатить только часть изменений).
- При частых изменениях курса его снапшоты могут в теории занимать много места в БД, так как они хранят все свои блоки, но на практике это вряд ли будет проблемой.

---

### 4. Мягкая + оптимистичная блокировка, отдельные запросы, снапшоты курсов, хранение промежуточных этапов редактирования

Всё вышеописанное, но в придачу с сохранением всей истории небольших изменений между снапшотами.

- Создаётся таблица в БД, хранящая последовательность атомарных изменений курса. Хранить это как полные снимки курса или его частей слишком ресурсозатратно и не эффективно, поэтому лучше сохранять изменения в виде диффа между этими промежуточными версиями редактируемого курса, либо в виде каких-то команд с производимыми действиями.
- Эти промежуточные изменения сохраняются только для последнего снапшота, либо для нескольких последних снапшотов.
- Каждое небольшое изменение элементов курса, сделанное пользователем в процессе редактирования, (изменение порядка блоков, их добавление, удаление, изменение содержимого) сохраняется в этой таблице, и пользователь может перемещаться по этим изменениям.
- Если пользователь откатился на некоторое число изменений назад и из этого состояния внёс новое изменение, то вся линия последующих изменений перезаписывается новым (как обычно в большинстве редакторов).
- Нужно определиться, насколько маленькие изменения стоит сохранять. Например, чтобы при редактировании содержимого блока с текстом можно было откатиться не просто до момента начала редактирования конкретно этого блока, а прям до определённых этапов процесса написания текста.

#### Плюсы решения

- Все плюсы решения, описанного выше.
- Пользователь может максимально удобно перемещаться по истории изменений.

#### Минусы решения

- Большая нагрузка на сеть и БД при слишком частых и мелких изменениях (но является ли это проблемой?).
- В варианте с отслеживанием изменений на уровне содержимого блоков (например текста) фронтенд должен уметь автоматически детектить эти промежуточные изменения и правильно отправлять их на бэкенд.
- Сложность реализации.

---

### 5. Снапшоты курсов с copy-on-write

Всё вышеописанное, но каждый из снапшотов курсов хранят не все его блоки, а только те, что были изменены в рамках соответствующей редакции курса.

- При создании снапшоты курса не хранят никаких блоков, и в процессе редактирования в снапшот добавляются только те блоки, которые были изменены.
- Затем эти снапшоты каким-то образом последовательно применяются к курсу, отражая его актуальное состояние.

#### Плюсы решения

- Снапшоты занимают меньше места в БД.

#### Минусы решения

- Дополнительные расходы на сборку всех снапшотов в один курс со всеми блоками.
- Необходимо как-то отдельно обрабатывать удаление блоков в снапшоте, так как простое отсутствие блока в случае copy-on-write будет восприниматься как отсутствие его изменений.

---

### 6. Одновременное совместное редактирование курса

Можно реализовать возможность одновременного редактирования одного курса несколькими пользователями. Для этого существует множество подходов, вот некоторые из рассмотренных:

- Блокировка на уровне блоков на всё время редактирования.
- Временная блокировка блоков только на время взаимодействия.
- Conflict-free Replicated Data Types (CRDT)

#### Плюсы решения

- Возможность редактировать курс одновременно несколькими пользователями.

#### Минусы решения

- **_ГИБЕЛЬ_**

## Принятое решение

**3. Мягкая + оптимистичная блокировка, отдельные запросы, снапшоты курсов**

- Было принято решение просто блокировать возможность редактирования курса, если в этот момент он уже редактируется кем-то другим, так как ситуация одновременного редактирования одного курса несколькими пользователями крайне редкая, но при этом требует чрезмерно сложной в реализации логики работы, что на данный момент не стоит затраченных усилий.
- Redis отвечает за мягкую блокировку курса с TTL и heartbeat, чтобы иметь возможность сразу предотвращать на фронтенде начало редактирования курса кем-то другим, а Postgres гарантирует финальную целостность данных на уровне БД.
- Фронтенд отправляет запросы при изменении каждого отдельного блока, а также с определённым интервалом отправляет heartbeat для поддержания блокировки.
- При начале редактирования курса создаётся его новый снапшот, который пока не будет виден студентам, и все сделанные изменения производятся над ним.
- Когда редактирование завершается, блокировка снимается и курс начинает ссылаться на этот новый снапшот.
- Механизмы хранения промежуточных этапов редактирования курса и добавления блоков в снапшот по copy-on-write могут иметь смысл, но пока не являются приоритетными, поэтому можно реализовать уже в будущем при необходимости.

## Положительные последствия

- Появится механизм редактирования курсов.
- Конфликты предотвращаются на раннем этапе.
- Данные защищены версионированием даже при сбое кэша или сети.
- Благодаря снапшотам и отдельным запросам для блоков риски потери данных сводятся к минимуму.
- Редактирование отдельного снапшота позволяет скрывать от студентов ещё не завершённые изменения курса.
- Появляется возможность откатывать изменения курса к состоянию предыдущих снапшотов.
- Остаются возможности для дальнейшего улучшения этого механизма.

## Негативные последствия

- Фронтенд должен поддерживать фоновые запросы (heartbeat) во время редактирования.

## Детали реализации

### 1. Изменения в таблицах Postgres

- Добавляется таблица `course_snapshots`, в которой хранятся все снапшоты курсов:

  ```sql
  CREATE TABLE course_snapshots (
      id uuid PRIMARY KEY DEFAULT uuidv7(),
      course_id uuid NOT NULL REFERENCES courses(id),
      parent_id uuid REFERENCES course_snapshots(id), -- parent snapshot
      version integer NOT NULL, -- serial number of the course edition
      created_by uuid NOT NULL REFERENCES users(id),
      created_at timestamp NOT NULL,
      is_available boolean NOT NULL DEFAULT true,

      CONSTRAINT course_version_unique UNIQUE (course_id, version)
  );
  ```

- Таблица `courses` хранит только метаданные курсов. В неё добавляются следующие поля:
  - `active_snapshot_id uuid NOT NULL REFERENCES course_snapshots(id)` - указывает на снапшот, который сейчас видят студенты.
  - `version integer NOT NULL DEFAULT 1` - используется для оптимистичной блокировки при завершении редактирования.

- Так как содержимое теперь привязано к конкретному снапшоту, то в таблицу `blocks` вносятся следующие изменения:
  - Помимо `id` добавляется поле `original_id uuid NOT NULL`, потому что иначе при копировании блоков в новый снапшот их ID изменятся и все ссылки на старые блоки поломаются. В это поле сохраняется значение `id` блока при его первом создании и остаётся неизменным в последующих снапшотах. Именно на это поле ссылаются внешние сущности, если возникает такая необходимость.
  - Поле `course_id` заменяется на `snapshot_id uuid NOT NULL REFERENCES course_snapshots(id)`.
  - Для оптимизации операций перемещения блоков при редактировании (чтобы при перемещении одного блока вверх не приходилось менять значения позиций у всех блоков ниже него) поле `position` заменяется на `lexo_rank varchar(64) NOT NULL` и используется лексикографический индекс для сортировки блоков.

### 2. Управление пессимистичными блокировками и метаданными сессий редактирования

Поскольку одновременное редактирование исключено, доступ к черновику регулируется монопольной пессимистичной блокировкой курса в Redis:

- При нажатии кнопки начала редактирования фронтенд делает запрос `POST /api/v1/courses/{course_id}/start_edit`. Бэкенд пытается установить ключ `lock:course:{course_id}` в Redis со значением `user_id` и TTL 60 секунд.
- Если ключ установлен успешно - доступ разрешен.
- Если ключ уже существует - бэкенд возвращает статус `423 Locked` и ID (или сразу имя) пользователя, который сейчас редактирует курс. Фронтенд блокирует интерфейс и выводит соответствующее предупреждение.

- Каждые 30 секунд фронтенд отправляет запрос `POST /api/v1/courses/{course_id}/heartbeat`. Бэкенд проверяет в Redis, что блокировка всё ещё принадлежит текущему пользователю, и возобновляет её TTL до 60 секунд.
- Если у преподавателя пропал интернет или он закрыл вкладку, через 60 секунд блокировка в Redis исчезнет сама.

- При успешной установке блокировки в Redis, после создания чернового снапшота также сразу создаётся запись с метаданными этой сессии редактирования, где ключ `session:course:{course_id}:user:{user_id}`, TTL 7 дней, а в значении хранится JSON:

  ```json
  {
    "draft_snapshot_id": "<uuid>",
    "initial_course_version": 3
  }
  ```

  Эта запись позволит в будущем легко восстановить сессию редактирования с незавершённым снапшотом, если TTL блокировки истечёт по ошибке.

- Если же при установке блокировки в Redis соответствующая запись с метаданными уже будет находиться, значит у пользователя осталась незавершённая сессия, которую можно попробовать восстановить. В случае успешного восстановления сессии возобновляем TTL этой записи.

### 3. Процесс редактирования

#### 1. Инициализация черновика

Как только преподаватель успешно захватил блокировку в Redis, бэкенд сначала проверяет, не осталось ли у этого пользователя незавершённой сессии редактирования:

1. Проверяется существование записи с ключом `session:course:{course_id}:user:{user_id}` в Redis.
   - Если такая запись есть, то бэкенд пытается восстановить незавершённый черновик по сохранённым метаданным. Для этого проверяется, соответствует ли текущая версия курса той, что была сохранена в `initial_course_version`.
     - Если версия соответствует, значит никто до этого пользователя не успел внести никаких своих изменений и его черновик всё ещё актуален. Восстанавливается блокировка в Redis для этого пользователя и фронтенду возвращается `draft_snapshot_id` - ID незавершённого снапшота этого пользователя, в котором он может продолжить свои изменения.
     - Если же версия не соответствует, значит этот черновик устарел. Бэкенд удаляет из Redis старую запись о сессии редактирования, после чего удаляет из БД этот черновик со всеми его блоками.
   - Если запись отсутствует, или черновик не удалось восстановить, то бэкенд создаёт новый черновой снапшот. Для этого выполняется следующая транзакция в Postgres:
     1. Вычисляется следующая по счёту версия относительно снапшота с `id = active_snapshot_id`.
     2. Создаётся новая запись в `course_snapshots` с вычисленным значением `version`, `is_available = false` и `parent_id = active_snapshot_id`.
     3. Копируются все блоки из текущего `active_snapshot_id` в только что созданный снапшот (`INSERT INTO blocks (...) SELECT ... WHERE snapshot_id = active_snapshot_id`).
     4. Фронтенду возвращается ID созданного чернового снапшота. Студенты этого снапшота не видят, так как поле `active_snapshot_id` в таблице `courses` всё ещё указывает на старый снапшот.

#### 2. Атомарные изменения блоков в процессе редактирования

Любое действие преподавателя на фронтенде отправляет отдельный запрос, который применяется к новому черновому снапшоту:

- **Добавление блока:** При запросе `POST /api/v1/blocks/{course_id}/blocks` создается новый блок с `snapshot_id` черновика. `original_id` задаётся равным сгенерированному `id`. Ему присваивается `lexo_rank` больший, чем у текущего последнего блока (блок появляется в самом низу).
- **Редактирование содержимого:** Запрос `PATCH /api/v1/blocks/{block_id}` позволяет обновить поле `data` - содержимое конкретного блока, а также `block_type`.
- **Перемещение (Drag & Drop):** Фронтенд отправляет запрос `PATCH /api/v1/blocks/{block_id}/move` с телом `{ "prev_block_id": "UUID", "next_block_id": "UUID" }`. Бэкенд вычисляет ранги переданных соседей из БД, генерирует промежуточный между ними `lexo_rank` и обновляет это значение у перемещённого блока.
- **Удаление:** При запросе `DELETE /api/v1/blocks/{block_id}` запись с блоком этого снапшота просто удаляется из таблицы `blocks` по её `id`.

Каждый такой запрос попутно проверяет на бэкенде наличие активной блокировки курса за этим пользователем в Redis. Если блокировка утеряна (например, из-за таймаута связи), бэкенд возвращает ошибку и запрещает изменять черновик.

#### 3. Перемещение по таймлайну снапшотов курса

Так как каждый сеанс редактирования курса сохраняется в БД в виде отдельного снапшота, то можно дать преподавателю возможность откатывать состояние курса к нужному снапшоту.

- Запрос `POST /api/v1/courses/{course_id}/undo_edit`:
  1. У нашего чернового снапшота `parent_id` изменяется на значение `parent_id` родительского снапшота, `version` ставится равной версии родительского снапшота (декрементируется), и все блоки заменяются на блоки "деда" (родителя для снапшота с `id` равным нашему изначальному `parent_id`).
  2. После этого выполняется проверка значения `parent_id` у нового родителя нашего снапшота.
     - Если `parent_id` родителя оказывается равен `NULL`, значит мы достигли самого начала таймлайна и дальше двигаться не можем. В этом случае возвращаем в ответе `can_undo = false` и фронтенд делает соответствующую кнопку неактивной. Если после этого всё равно придёт запрос на `undo_edit`, то возвращаем ошибку `422 Unprocessable Entity`.
     - Если `parent_id` родителя не равен `NULL`, то возвращаем в ответе `can_undo = true`.
- Запрос `POST /api/v1/courses/{course_id}/redo_edit`:
  1. Ищется снапшот (назовём его последующим), у которого `is_available = true` и при этом `parent_id` равен `parent_id` нашего чернового снапшота, и соответственно в нашем снапшоте ставится `parent_id` равным `id` этого "последующего" снапшота, `version` инкрементируется, и все блоки заменяются на блоки "последующего" снапшота. Благодаря тому, что у черновика значение `is_available` во время редактирования равно `false`, то мы можем однозначно определить "последующий" снапшот, к котому хотим переместиться.
  2. После этого ищется ещё один снапшот, у которого `is_available = true` и `parent_id` равен новому `parent_id` нашего снапшота
     - Если такой снапшот не найден, значит мы достигли конца доступного таймлайна. В этом случае возвращаем в ответе `can_redo = false` и фронтенд делает соответствующую кнопку неактивной. При повторном запросе `redo_edit` в этом случае также возвращаем `422 Unprocessable Entity`.
     - Если снапшот найден, то возвращаем `can_redo = true`.

При этих запросах также проверяется наличие активной блокировки курса за этим пользователем в Redis.

#### 4. Завершение редактирования и публикация нового снапшота

Когда преподаватель нажимает на завершение редактирования, фронтенд отправляет запрос `POST /api/v1/courses/{course_id}/publish`,и выполняется заключительная транзакция в Postgres:

1. Выполняется проверка версии курса для защиты от race condition:

   ```sql
   UPDATE courses
   SET active_snapshot_id = :new_snapshot_id, version = version + 1
   WHERE id = :course_id AND version = :expected_version;
   ```

   Если `RowsAffected == 0`, транзакция откатывается, возвращается `409 Conflict` (сигнал о том, что версия курса изменилась). Если же версия курса правильная, то `active_snapshot_id` курса устанавливается равным `id` нашего снапшота.

2. После этого у всех снапшотов, версия которых больше или равна версии нашего снапшота, поле `is_available` устанавливается в `false`:

   ```sql
   UPDATE course_snapshots
   SET is_available = false
   WHERE course_id = :course_id
   AND version >= :new_snapshot_version;
   ```

3. Затем у нашего снапшота значение `is_available` устанавливается в `true`:

   ```sql
   UPDATE course_snapshots
   SET is_available = true
   WHERE id = :new_snapshot_id;
   ```

   Таким образом наш снапшот полностью заменяет собой больше недоступную ветку таймлайна снапшотов.

4. При успешном обновлении бэкенд удаляет из Redis блокировку и метаданные сессии редактирования этого пользователя. Теперь обновленный курс со всеми новыми блоками мгновенно становится доступен студентам.

#### 5. Отмена изменений и механизм восстановления незавершенной сессии

- Если пользователь нажимает кнопку отмены всех незавершённых изменений, фронтенд отправляет запрос `POST /api/v1/courses/{course_id}/cancel_edit`, и бэкенд удаляет из Redis блокировку и метаданные сессии, а также полностью удаляет черновой снапшот из `course_snapshots` со всеми его блоками.
