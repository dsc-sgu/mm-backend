# Выбор архитектуры сдачи заданий (попыток) через Git и UI

## Проблематика

Необходимо реализовать механизм сдачи попыток выполнения заданий для участников курса, поддерживающий два способа отправки: загрузку файлов через UI и прямой push в Git. Основной конфликт заключается в необходимости балансировать между требованиями к чистым диффам, линейной истории Git и простой модели для пользователей, с одной стороны, и поддержкой нескольких заданий, доработок отклоненных попыток и параллельной работы над разными задачами — с другой.

## Факторы, влияющие на решение
*Примечание: некоторые факторы уже соответствуют конкретным рассматриваемым решениям, что указано ниже:*

- Поддержка двух способов отправки (UI-загрузка файлов и Git-push) с единой внутренней моделью попытки 
- Отслеживание истории попыток, включая доработки отклоненных заданий 
- Линейная история Git, чистые диффы в рамках отдельных заданий/групп 
- Ограничение или запрет force-push для предотвращения потери истории попыток 
- Поддержка параллельной работы над несвязанными заданиями без конфликтов 
- Валидация структуры заданий (фиксированные пути/произвольная структура) 
- Минимальные требования к знаниям Git у студентов 
- Независимость данных попыток от истории Git 
- Валидация типов файлов (однофайловые/многофайловые задания) 
- Обработка Git-событий (вебхуки, теги, коммиты) 

---

## Рассматриваемые решения

### Отправка попыток как загрузка файлов без интеграции с Git

Механизм, при котором попытка — это просто загрузка файлов для конкретного задания `(participant_id, course_id, task_id)` через UI, без привязки к Git. Git-push игнорируются или обрабатываются как отдельные сущности без общего с UI модели.

- Попытка через UI сохраняет файлы в хранилище, записывает метаданные в БД.
- Git-push не связаны с попытками, история коммитов не учитывается.
- Не поддерживается валидация структуры для заданий с фиксированными путями.

#### Плюсы решения
- Максимально простая реализация для первой версии.
- Не требует интеграции с Git-сервером.

#### Минусы решения
- Нет единой модели для UI и Git-отправок.
- Нет отслеживания Git-истории и диффов.
- Невозможно валидировать структуру заданий, требующих фиксированных путей.
- Нет истории изменений для заданий, сдаваемых через Git.
- Не поддерживает разные типы заданий (однофайловые/многофайловые с произвольной структурой).

---

### Определение попыток по Git-коммитам

Механизмы определения того, какой Git-коммит считать новой попыткой при прямом push студента.

#### Любой push в main считается новой попыткой
- Система обрабатывает все push-события в ветку main, каждый новый коммит считается попыткой.
- Диффы считаются по всему репозиторию.

##### Плюсы решения
- Максимально простая логика для Git-отправок.

##### Минусы решения
- Непонятно, какой именно коммит считать попыткой при нескольких коммитах в push.
- Диффы смешивают изменения разных заданий, если в репозитории несколько заданий.
- Нет явной привязки попытки к конкретному заданию.

---

#### Подрешение: Annotated теги по шаблону `attempt-%t`

Попытки помечаются тегами по шаблону `attempt-%t`, где `%t` — номер задания, при этом название тега — номер попытки. Система определяет попытки по тегам в ветке main.

- Студент создает тег после коммита в main.
- Система обрабатывает теги, считает диффы по всему репозиторию.

##### Плюсы решения
- Явное отслеживание номеров попыток через теги.
- Простая модель для студентов: только пуш в main и создание тегов.

##### Минусы решения
- Студенту нужно помнить номер последней попытки для создания нового тега.
- Теги могут быть отправлены не в том порядке, на один коммит можно повесить несколько тегов.
- Диффы считаются по всему репозиторию, смешивая изменения разных заданий.
- Непонятно, как обрабатывать неправильные теги.

---

#### Подрешение: Автоматические теги

После отправки пользователем попытки с каким-либо тегом, система перезаписывает тег по шаблону, как в предыдущем решении.

- Студент создает любой annotated тег к коммиту, который подразумывается попыткой.
- Система считывает коммит с тегом и перезаписывает его название и текст.

##### Плюсы решения
- Студенту не нужно помнить номера попыток и следовать шаблону.
- Попытки фиксируются автоматически, меньше ошибок пользователя.

##### Минусы решения
- Требует настройки вебхуков Git-сервера и логики обработки Git-событий.
- Нужно корректно определять, к какому заданию/task-группе относится коммит.

---

### Структура репозиториев и веток

#### Отдельные ветки или репозитории на каждое задание

Каждое задание имеет свой репозиторий или отдельную ветку в общем репозитории курса. Студенты работают в ветках заданий, создают merge requests (MR) для сдачи попытки.

- Для каждого задания создается отдельная ветка, студент делает коммиты в неё.
- Попытка создается при открытии MR, который затем сливается в main после проверки.
- Поддержка ребейзов и форс-пушей для исправления истории ветки.

##### Плюсы решения
- Изолированная история для каждого задания, чистые диффы.
- Удобная модель для крупных проектов с зависимостями между заданиями.

##### Минусы решения
- Слишком сложная модель для студентов: нужно уметь работать с ветками, MR, ребейзами.
- Требует реализации полноценной логики MR, управления ветками, обработки конфликтов.
- Форс-пуши могут переписывать историю попыток, что усложняет их учет.
- UI-отправка файлов плохо вписывается в эту модель.
- Зависимости между ветками заданий усложняют ребейзы.

---

#### Task-группы с директориями в едином репозитории main

Курс разбивается на task-группы (логические группы связанных заданий), каждая группа соответствует директории в едином репозитории курса. Все коммиты идут в ветку main.

- Task-группы и задания описываются в конфигурационном файле курса.
- Диффы считаются только для директории конкретной task-группы, а не всего репозитория.
- Внутри одной группы задания сдаются последовательно, разные группы можно делать параллельно.

##### Плюсы решения
- Чистые диффы в рамках конкретных заданий/групп.
- Параллельная работа над разными task-группами без конфликтов.
- Линейная история main, простая модель для студентов.

##### Минусы решения
- Нужно навязывать жесткую структуру директорий репозитория.
- Требует реализации логики определения task-группы по измененным директориям.

---

#### Отдельные репозитории для каждой task-группы

Каждая task-группа имеет свой отдельный репозиторий. Внутри репозитория task-группы все задания сдаются последовательно, репозитории task-групп можно редактировать параллельно.

##### Плюсы решения
- Полная изоляция между task-группами, параллельная работа без конфликтов.
- Проще настраивать права доступа на уровне репозиториев.

##### Минусы решения
- Студенту нужно работать с несколькими репозиториями для курса.
- Усложняет настройку Git-сервера (несколько репозиториев вместо одного).

---

### Воркфлоу сдачи заданий

#### Merge Request на каждую попытку

Каждая попытка сдачи задания оформляется как отдельный Merge Request (MR) в main. Попытка создается при открытии MR, проверяется, затем сливается в main.

##### Плюсы решения
- Красивый воркфлоу с проверкой перед слиянием.
- Изолированная история каждой попытки.

##### Минусы решения
- Сильно усложняет систему: нужно реализовывать MR-логику, управление ветками, обработку rebase.
- Нужно объяснять студентам, как работать с ветками и MR.
- UI-отправка файлов плохо ложится в такую модель.

---

#### Идея: Очередь попыток следующих заданий до проверки предыдущих в task-группах

Если студент пытается сдать следующее задание в группе до проверки предыдущего, попытка ставится в очередь. Она автоматически фиксируется (создается коммит, запись в БД) только после того, как предыдущее задание будет проверено и принято.

##### Плюсы решения
- Студент может работать над следующими заданиями, не дожидаясь проверки предыдущих.
- Сохраняется последовательность сдачи внутри группы.

##### Минусы решения
- Усложняет логику обработки попыток (нужно хранить очередь, отслеживать статусы предыдущих заданий).
- Студент может не понимать, что его попытка находится в очереди.

### Конфигурация и модели данных

#### Правила структуры курса и repo_id в коде

Правила структуры task-групп, путей заданий, а также логика формирования repo_id жестко прописаны в коде системы.

- repo_id формируется как `participant_id + course_id + task_id`.
- Структура курса меняется только через правки кода.

##### Плюсы решения
- Простая реализация для первой версии.

##### Минусы решения
- Сложно менять структуру курса, добавлять новые task-группы без правок кода.
- repo_id не соответствует концепции task-групп, если несколько заданий входят в одну группу.

---

#### Конфигурационный файл курса (YAML/KDL)

Структура курса, task-групп, заданий и их путей описывается в конфигурационном файле (YAML или KDL), который хранится вместе с курсом.

- Пример конфигурации YAML:
  ```yaml
  groups:
    - id: "basics"
      path: "01_basics"
      tasks:
        - id: "hello_world"
        - id: "loops"
    - id: "networking"
      path: "02_networking"
      tasks:
        - id: "socket_server"
  ```
- Конфигурация загружается системой при обработке попыток для валидации путей и определения task-групп.

##### Плюсы решения
- Легко менять структуру курса без правок кода.
- Преподаватели могут самостоятельно настраивать структуру курса.
- Позволяет задавать шаблоны путей для заданий внутри конфигурации.

##### Минусы решения
- Требует реализации парсинга конфигурационного файла.
- Нужно валидировать корректность конфигурации.

---

#### Раздельные модели для UI и Git-отправок

UI-отправка файлов и Git-push обрабатываются как две разные сущности с разными моделями попыток, правилами истории и диффов.

##### Плюсы решения
- Можно оптимизировать каждую модель под конкретный способ отправки.

##### Минусы решения
- Две разные модели усложняют бэкенд-логику, проверку и отображение попыток.
- Студенты и преподаватели видят разные типы попыток для одного курса.

---

#### repo_id соответствует task-группе

Идентификатор репозитория `repo_id` привязывается не к конкретному заданию, а к task-группе. Это позволяет нескольким заданиям внутри одной группы использовать один репозиторий.

##### Плюсы решения
- Соответствует концепции task-групп, несколько заданий используют один репозиторий.
- Упрощает управление репозиториями (меньше репозиториев, чем заданий).

##### Минусы решения
- Требует пересмотра логики формирования repo_id и привязки попыток к репозиториям.
